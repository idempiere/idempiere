# iDempiere contribution workflow

iDempiere uses a fork-and-branch model with Jira tickets. Every change maps to exactly one ticket at https://idempiere.atlassian.net.

Reference: https://docs.idempiere.org/docs/basic-development/contributing-to-core/git-workflow

## 1. Before writing code

- Confirm the Jira ticket number (`IDEMPIERE-####`). If there is none, stop and ask the developer. Do not invent one. To draft a ticket, see `idempiere-jira-tickets`.
- Check the remotes. `origin` should be the developer's fork, `upstream` should be `https://github.com/idempiere/idempiere.git`:
  ```bash
  git remote -v
  ```
- Sync `master` with upstream:
  ```bash
  git checkout master
  git pull --ff-only upstream master
  git push origin master
  ```
  If the fast-forward fails, local `master` has commits of its own, which hard rule 1 forbids. Stop and tell the developer instead of merging.
  After pulling, suggest that the developer run `bash RUN_SyncDBDev.sh` to apply new migration scripts to the local database (see `idempiere-headless-build-run`).
- If the ticket needs dictionary or database changes, read `idempiere-database-changes` **before** coding. The developer must request Centralized IDs and generate scripts from the UI.

## 2. Branch

```bash
git checkout -b IDEMPIERE-1234-short-description
```

- Never commit to `master`, not even in the developer's fork.
- One branch per ticket.

## 3. Commit

- Format: `IDEMPIERE-#### Short description` (the ticket title or a concise summary). Example from history: `IDEMPIERE-7143 - Show the pencil edit button on color fields`.
- Each commit relates to the ticket. Do not mix unrelated changes.
- If the change needs a refactoring, make it a **separate commit** from the actual fix, so reviewers can read each on its own.
- Stage only the files you intended to change. Check `git status` and `git diff --staged` for stray files (`idempiere.properties`, `.classpath`, `jettyhome`, IDE files, logs, `target/`).
- Migration scripts generated by the developer belong in the same commit or PR as the code that needs them.

## 4. Before pushing: self-check

Run the checklist in `idempiere-pr-review` against your own diff. At minimum:

- Code builds (`./mvnw verify`, or a targeted build, see `idempiere-headless-build-run`).
- Existing unit tests still pass, and new logic or bug fixes have a test where feasible (`idempiere-unit-tests`).
- PostgreSQL and Oracle migration files are both present if there are DB changes.
- No public or protected signature was changed or removed without an overload, unless the developer decided on a breaking change and it is documented as one.

## 5. Push and open the pull request

```bash
git push origin IDEMPIERE-1234-short-description
```

Open the PR against `idempiere/idempiere` `master`. The PR body must follow `pull_request_template.md`:

- **First line: the Jira ticket link**, e.g. `https://idempiere.atlassian.net/browse/IDEMPIERE-1234`
- Purpose and impact of the change.
- Steps to reproduce the problem or business scenario (on GardenWorld if possible).
- Tests performed and test cases covered. State honestly what was **not** tested.
- Other use cases that may be affected (collateral analysis).
- Required test data, 2Packs or migration scripts.
- Design explanation for non-obvious choices.
- Unit tests added or updated.
- The checklist from `pull_request_template.md`, with boxes checked only when true.

If the developer uses the GitHub CLI, draft the body to a file and show it to them before running `gh pr create`. Opening a PR is a public action, so confirm with the developer first.

## 6. Does this PR need documentation?

Following the PR template, documentation in the docs repository (https://github.com/idempiere/idempiere.github.io) is required when the change is:

- a **new feature**: a New Feature page explaining what it does and how to use it;
- a **breaking change**: a clear explanation of the impact for the community;
- an **improvement that changes how users interact with the system** or the outcome of a process (pure performance work usually needs none).

The documentation is written in the docs repository, on its own branch and PR, following that repo's own agent instructions. In the core PR, link the docs PR or state why no docs are needed. Documentation must live in the project docs, not in private PDFs or company sites.

## 7. Review feedback

- The first review often comes from CodeRabbit. Evaluate each comment on its merits: apply the valid ones, and reply with reasoning to the ones that don't apply.
- Answer human reviewers promptly. PRs or tickets with no contributor reply for 60 days can be marked stale and closed 7 days later.
- Push fixes as new commits to the same branch, keeping the `IDEMPIERE-####` prefix. If upstream moved and there are conflicts, resolve them.

## Don'ts

- Don't force-push or rewrite published history unless the developer asks.
- Don't open, close or comment on PRs or Jira tickets without the developer's confirmation.
- Don't bundle a new feature and a refactoring into one commit.
