# Migration script review checklist

Use this to review scripts **generated by the developer** (or included in a PR under review). Report findings; do not rewrite the scripts yourself.

## Files
- [ ] One file in `migration/iD<current>/postgresql/` and one with the **same name** in `migration/iD<current>/oracle/`.
- [ ] Name matches `yyyyMMddHHmm_IDEMPIERE-####.sql`, and the ticket number matches the branch/PR.
- [ ] Timestamp is later than the newest script already in the current version folder (`ls migration/iD<current>/postgresql/*.sql | tail -3`, e.g. `iD14`). If upstream added newer scripts meanwhile, the developer may need to rename the file (and update the `register_migration_script` argument to match).
- [ ] No other files were touched under `migration/` (e.g. `build.xml`, older scripts).

## Header
- [ ] Line 1: `-- IDEMPIERE-#### <description>`.
- [ ] Line 2: `SELECT register_migration_script('<exact file name>') FROM dual;`.
- [ ] Oracle only: `SET SQLBLANKLINES ON` and `SET DEFINE OFF` follow.

## Content
- [ ] Every statement belongs to this ticket. No leftovers from other work done with logging on.
- [ ] No failed statements (logging records them too). Ask the developer whether every statement ran successfully.
- [ ] No trial-and-error noise: a record inserted, then updated several times, then deleted. Ask for a clean regeneration if it is confusing.
- [ ] Dictionary records use `AD_Client_ID=0`, `AD_Org_ID=0`, `EntityType='D'`.
- [ ] New IDs come from the official Centralized ID range (ask the developer if unsure).
- [ ] Each statement ends with the `;` line produced by the generator.
- [ ] DDL (`ALTER TABLE ... ADD COLUMN`, `CREATE TABLE`) is present when columns or tables were added, and matches the column definition (type, default, NOT NULL, CHECK for Y/N).
- [ ] PostgreSQL and Oracle files are equivalent (same records, DB-specific DDL syntax).
- [ ] Translation tables (`*_Trl`) are handled the way the generator does it; nothing hand-added.

## After applying
- [ ] `bash RUN_SyncDBDev.sh` on a clean database runs the scripts without errors (check `/tmp/SyncDB_out_*`).
- [ ] Model classes (`X_*` / `I_*`) were regenerated if columns changed, and the regenerated files contain only the expected changes.
