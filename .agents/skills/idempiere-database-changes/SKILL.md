# Database and Application Dictionary changes

Reference: https://docs.idempiere.org/docs/basic-development/contributing-to-core/changing-the-database

## The rule: you do not write migration scripts

iDempiere core uses **Centralized ID management**: every new `AD_*` record in core gets an officially assigned ID, and migration scripts are **generated by iDempiere itself** while the developer edits the dictionary in the UI with migration logging on. A hand-written script, or an invented `*_ID` / `*_UU`, bypasses Centralized ID management and can clash with IDs used by other contributors, so the core team rejects it.

Therefore you must **never**:

- create or edit `.sql` files under `migration/` with `INSERT`/`UPDATE`/`DELETE` on `AD_*` tables;
- invent or guess `AD_*_ID` values or `*_UU` UUIDs;
- write `ALTER TABLE` / `CREATE TABLE` DDL for core tables;
- edit generated `X_*.java` / `I_*.java` model classes by hand;
- "fix" a generated script by rewriting its statements yourself. Point out the problem and let the developer regenerate or correct it.

What you **do**: detect that AD or DB work is needed, specify it precisely, guide the developer through generating it, review the output, and write the Java code that uses it.

## Step 1: detect and stop

As soon as you notice the task needs any dictionary or schema change (new column, message, process parameter, SysConfig, reference list value, etc.), **stop coding that part** and tell the developer. Ideally do this before writing Java code.

## Step 2: write the specification for the developer

Give the developer an exact list of what to create in the UI, for example:

| Object | Details |
|---|---|
| Element | ColumnName `IsMaximizable`, Name/PrintName `Is Maximizable`, EntityType `D` |
| Column | Table `PA_DashboardContent`, Reference `Yes-No`, Default `Y`, Mandatory, Updatable |
| Field | Window *Dashboard Content*, tab *Dashboard Content*, after field X |
| Message | Value `NoPendingActivities`, Type `I`, Text `No pending Activities` |

Include table, column name, reference, length, default, mandatory, and where the field shows up. Use iDempiere naming conventions (`Is*` for booleans, `*_ID` for FKs, EntityType `D` for core).

## Step 3: guide the developer through generation

Explain the steps; the developer performs them:

1. Request official IDs following the Centralized ID guide (https://wiki.idempiere.org/en/Centralized_ID_Management) or by contacting the core team.
2. Log in to the iDempiere web UI as **System Administrator**.
3. Open **Preference** (next to *Change Role*) and enable **Dictionary Maintenance** and **Log Migration Scripts**.
4. Fill in **Migration Script Comment** with the ticket and short description, e.g. `IDEMPIERE-5409 Dashboard Content - Maximizable checkbox`.
5. Create or modify the dictionary objects from Step 2 (and use *Synchronize Column* where needed).
6. iDempiere writes the scripts to the local migration folder, e.g. `migration/iD14/postgresql/` and `migration/iD14/oracle/`.
7. If columns or tables changed, regenerate the model classes (`X_*` / `I_*`) with the model generator (`org.adempiere.base-feature/model.generator.launch` or the developer's usual method).

Then wait until the developer says the scripts are generated.

## Step 4: review the generated scripts

Review only; report problems back to the developer. Use `references/script-review-checklist.md`. The key checks:

- **Both** a PostgreSQL and an Oracle file exist, with the same file name, in the current `migration/iD<version>/` folder.
- File name `yyyyMMddHHmm_IDEMPIERE-####.sql`, and its timestamp is later than the newest existing script in that folder.
- First line is `-- IDEMPIERE-#### <description>`, second is `SELECT register_migration_script('<same file name>') FROM dual;`.
- Oracle file contains `SET SQLBLANKLINES ON` / `SET DEFINE OFF` after the header.
- **Failed statements are logged too.** Look for statements that failed, duplicates, trial-and-error edits, changes reverted later in the same script, and records unrelated to the ticket. Ask the developer to remove them.
- IDs fall in the officially assigned range, not in a local/custom range. If unsure, ask the developer to confirm they used Centralized IDs.
- EntityType is `D` for core objects.
- No `AD_Client_ID` other than 0 for dictionary records, unless intended.
- PostgreSQL and Oracle files contain the equivalent set of changes.

Example of a correctly generated header (PostgreSQL):

```sql
-- IDEMPIERE-7100 Web Client Desktop Refresh
SELECT register_migration_script('202609181745_IDEMPIERE-7100.sql') FROM dual;

-- Sep 18, 2026, 5:45:29 PM MYT
INSERT INTO AD_Message (...) VALUES (...)
;
```

## Step 5: apply locally and write the code

- The developer applies the scripts with `bash RUN_SyncDBDev.sh` (see `idempiere-headless-build-run`). On a database where the dictionary was edited, the scripts are already applied.
- Now write the Java that uses the new objects, through the regenerated `X_*` getters/setters and `COLUMNNAME_*` constants (see `idempiere-core-coding-standards`).
- If the feature needs sample data in GardenWorld, that is also generated by the developer, not hand-written.
- The generated scripts are committed together with the code, in the same PR (see `idempiere-contribution-workflow`).

## Unit tests and IDs

Tests may need IDs of existing GardenWorld records. Add them to `org.idempiere.test/src/org/idempiere/test/DictionaryIDs.java` by looking up the **existing** ID and UUID in the database. Never invent them. See `idempiere-unit-tests`.
